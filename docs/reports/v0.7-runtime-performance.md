# Rapport runtime — durcissement `v0.7-F2`

État au 24 septembre 2026. Mesures historiques de F2, sans validation clinique. Le
[rapport F3](v0.7-f3-runtime-latency.md) décrit le durcissement ultérieur de la latence.

## Périmètre et protocole

La base mesurée est **le vrai snapshot local** `v0.7.0-general-dev-unreviewed`, hash de contenu
`bfda708aba44dcc5d12896ac7523d9d6bb577dea53bdc3810e499c15f64b1fb0`, DuckDB proche
de 2 Go. Un processus Python 3.11 Windows frais effectue, dans cet ordre : création du service,
vérification forte du manifeste/Parquet/DuckDB, recherche UI `cough` (limite 20), création ou
réutilisation de la stratégie, deux diagnostics du cas synthétique
`examples/general/rare-multisystem.json`, puis `question next`. Les résultats sont hashés après
`model_dump_json()` puis relâchés et collectés entre les phases. Les temps sont muraux ; RSS,
maximum RSS du processus et mémoire privée proviennent de `GetProcessMemoryInfo`. L'exécution
après changement bloque explicitement les connexions réseau.

Avant modification, les sept cas de `examples/general/` ont été exécutés sur l'ancienne stratégie
complète et leurs diagnostics et questions hashés. Le fichier versionné
`tests/golden/v0.7-general-v1-sha256.json` contient uniquement leurs empreintes et nombres de
candidats, sans dump médical ni donnée patient. Le script
`scripts/compare_general_v1_runtime.py` permet de les recontrôler sur le snapshot local.

Le pic RSS est réduit de **78,4 %** et le RSS final de **81,1 %**. Les 799 candidats du cas
multi-système et les empreintes complètes des deux diagnostics et de la question sont inchangés.
Les sept cas confirment 7/7 diagnostics et 7/7 questions identiques, y compris abstentions,
ordre, scores, contributions, mappings, provenance, reçus et motifs d'arrêt : leur JSON complet est
comparé par SHA-256. Les trois diagnostics scorés supplémentaires passent de 175–226 s à 48–51 s
sur cette passe. Les cas abstention prennent 0,2–0,5 s au lieu de moins de 0,05 s ; la question
reste un peu plus lente que l'ancien index Python déjà chargé.

Les temps muraux ne sont pas un benchmark clinique ni une garantie inter-machine : le cache disque
et la charge Windows varient entre passes. La réduction mémoire est le résultat prioritaire.

## Architecture et intégrité

`src/latros/knowledge/repository_v2.py` vérifie toujours SHA-256 de chaque table Parquet et du
DuckDB à l'ouverture, puis ouvre le runtime en lecture seule. Il centralise les requêtes ciblées
pour résolution, génération, scoring, provenance, questions et concepts UI. Une projection
temporaire DuckDB des dérivations et des appartenances aux familles accélère les jointures sans
modifier les fichiers figés ni créer un index Python global. Le cache applicatif retient au plus
deux objets repository légers et refuse la réutilisation si taille ou métadonnées d'un fichier
vérifié changent ; DuckDB peut néanmoins conserver ses propres buffers après diagnostic.
`store_v2.py`, son hash de pipeline, le manifeste et le profil ne sont pas modifiés.

La présélection conserve exactement l'ensemble scoré : `_aggregate_families()` ne peut renvoyer
un score que s'il existe au moins une contribution numérique dans une famille agrégeable et
autorisée par le profil ; une contribution n'est numérique que pour une observation `assessed`,
`present/absent`, de même concept et de même relation que l'assertion. La requête recherche
précisément ces conditions puis le calcul historique évalue toutes leurs assertions, y compris
les contributions `unknown`. `generate()` expose toujours l'ensemble et les métadonnées
historiques de candidats ; seul le travail interne de scoring est ciblé.

La stratégie complète historique reste dans `general_v1.py` comme oracle de tests ; la CLI et
l'interface utilisent la sous-classe paresseuse. Les mathématiques, l'abstention, la couverture,
les familles, les questions et la provenance ne sont pas versionnées autrement.

## Vérifications et limites

- Ruff, format, mypy strict, schémas et registres validés ; suite locale 150 tests verts.
- Tests synthétiques avec réseau non-loopback bloqué ; profil du vrai snapshot avec toute
  connexion bloquée. Les empreintes réelles des sept cas sont identiques.
- Build et inspection de l'identifiant v0.7 existant exécutés avec `uv --offline`, sans changement
  des hashes de contenu, de pipeline ou du manifeste. Ce contrôle relit les sources locales ; il
  ne crée pas un nouveau snapshot.
- Interface HTTP locale liée à `127.0.0.1` : page, capacités, recherche de concepts, deux
  diagnostics (799 candidats), détails de provenance, question adaptative, reprise de session et
  bascule vers `v0.2.0 + semantic_v1` puis retour vérifiés sur le snapshot réel ;
  `safety_status: not_evaluated` reste visible. La commande CLI `question next` offline réussit.
- L'ancienne base ORL `v0.5.0-dev-unreviewed` n'est pas reconstruite sur ce PC ; ses tests de
  régression synthétiques restent verts. Aucun artefact ORL n'entre dans le snapshot v0.7.
- Le runtime v2 historique stocke surtout `id/payload_json`. Certaines requêtes scannent encore
  plusieurs centaines de milliers de lignes ; le diagnostic complet de 799 candidats et toute
  leur provenance occupent encore environ 2 Go de RSS et 86–89 s. Une projection persistante ou
  un changement du format demanderait une tranche séparée et, si le build change, un nouvel ID
  de snapshot. Aucune réduction de vérification d'intégrité ou de provenance n'a été faite.
- `clinical_validation: false`, `publishable: false`, `research_unreviewed: true`, zéro assertion
  approuvée et `safety_status: not_evaluated` restent les seuls statuts légitimes. La revue
  clinique `v0.7-G` n'a pas commencé.

Depuis la racine du dépôt, après installation et acquisition locale des sources :

```text
uv run --offline --no-sync python scripts/compare_general_v1_runtime.py --output data/staging/v0.7-f2/check.json --expected tests/golden/v0.7-general-v1-sha256.json
uv run --offline --no-sync python scripts/profile_general_v1_runtime.py --output data/staging/v0.7-f2/profile.json
```

Ces sorties sous `data/staging/` sont locales, ignorées par Git et ne changent pas le snapshot.

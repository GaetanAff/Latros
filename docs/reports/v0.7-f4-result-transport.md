# `v0.7-F4` — transport résumé et détail à la demande

Mesures d'ingénierie Windows du 25 septembre 2026. Aucune validation médicale. Le snapshot
`v0.7.0-general-dev-unreviewed`, son hash
`bfda708aba44dcc5d12896ac7523d9d6bb577dea53bdc3810e499c15f64b1fb0`, le profil et
les mathématiques de `general_v1` ne changent pas.

## Problème et contrat

Après F3, le diagnostic du grand cas fictif dure environ 15,6 s, mais la réponse HTTP complète
prend encore plus de 20 s et transporte environ 206 Mo pour 3 650 candidats. Le parcours simple
n'affiche que quelques rangs. Il demande maintenant `?view=summary` ; la reprise utilise
`/runs/{run_id}/summary` et le clic « Voir pourquoi » utilise
`/runs/{run_id}/candidates/{candidate_id}`. La projection contient les statuts, le périmètre,
la couverture, l'abstention, `research_unreviewed`, `safety`, le nombre total de candidats et
au plus 20 rangs. Aucun pourcentage ni diagnostic calibré n'est ajouté.

Le résultat intégral et son reçu restent sous `data/staging/.../runs/<id>.json`, disponibles
par la route complète historique pour `/expert`. Un index auxiliaire par run retient les
offsets des candidats et le SHA-256 du fichier ; la lecture de détail ne désérialise qu'un
candidat. Un ancien run sans index utilise le chemin complet de compatibilité. Le SHA-256 du
run est revérifié avant chaque lecture indexée. L'index n'est pas une preuve clinique.

## Protocole et mesures

Même PC, même snapshot, même session **synthétique** archivée sous
`data/staging/ui-smoke-sessions-20260925/` : 3 observations, une réponse antérieure, 3 650
candidats. Les sessions de mesure sont isolées et éphémères sous `data/staging/`. Les scripts
bloquent les connexions non-loopback. Les durées sont des exécutions fraîches, sans contrôle
strict des caches OS ; elles ne constituent pas un SLA. F3 a mesuré la taille du résultat
intégral ; F4 mesure les octets de la réponse HTTP résumé.

| Mesure | Avant F4 | Après F4 |
| --- | ---: | ---: |
| Route diagnostic, grand cas | 22,912 s | 18,538 s |
| Résultat intégral / réponse initiale | 206 362 327 octets de résultat, réponse complète | 14 072 octets HTTP résumé |
| Détail du premier candidat | inclus dans la réponse complète | 198 312 octets ; 0,112 s |
| Reprise de la vue résumé | run complet | 9 363 octets ; 0,098 s |
| Question | ~5,2 s | 5,191 s ; 19 324 octets |
| Run complet local | conservé | 206 366 522 octets pour cet essai |

La première version de F4 mesurait 20,817 s pour la route résumé. Éviter une seconde copie
Pydantic de l'arbre de candidats lors de l'écriture a réduit cette durée à 18,538 s. Le
gain HTTP mesuré par rapport aux 22,912 s avant F4 est de 4,374 s (~19 %). La taille
initiale baisse de quatre ordres de grandeur ; le détail seul reste disponible. Le temps de
parsing et la mémoire du navigateur n'ont **pas** été instrumentés : la baisse attendue est
une inférence de la taille transférée, pas une mesure revendiquée.

La comparaison des sept cas d'or `general_v1` et les tests de session vérifient que le résultat
complet, l'ordre, les scores, la provenance, les mappings et les reçus ne changent pas. Le
nouveau résumé est une projection ; il ne remplace jamais le run scientifique.

## Limites

Le diagnostic et l'écriture du run complet restent dans la requête avant la réponse. Le grand
cas n'est donc toujours pas « quelques secondes ». `/expert` charge encore le run complet à
la demande, ce qui peut être lent sur ce cas. Une pagination experte ou un autre mécanisme de
persistance pourra faire l'objet d'une tranche distincte. Les runs historiques sans index
restent exacts mais leurs projections passent par la désérialisation complète.


La session synthétique archivée est un artefact local ignoré par Git ; elle n'est pas requise
pour les tests unitaires ou la CI. Aucun cas patient n'est conservé dans ce rapport.

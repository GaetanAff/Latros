# `v0.7-F3` — latence du diagnostic après question

Mesures d'ingénierie Windows du 25 septembre 2026, sans validation clinique. Le snapshot
`v0.7.0-general-dev-unreviewed` et son hash de contenu
`bfda708aba44dcc5d12896ac7523d9d6bb577dea53bdc3810e499c15f64b1fb0` restent figés.

## Protocole

`scripts/profile_v07_f3.py` ouvre un processus Python frais, bloque les connexions réseau,
chronomètre le service, l'ouverture/vérification du repository, une question puis un diagnostic,
et décompose les appels DuckDB, le scoring et la sérialisation. Il ne conserve que des durées,
empreintes et volumes, jamais le cas ou les assertions. Deux cas synthétiques ont servi :

- `examples/general/respiratory-common.json` (696 candidats) ;
- la session fictive archivée de l'essai UI « Fever, Barking cough », avec une réponse à une
  question, sous `data/staging/ui-smoke-sessions-20260925/` (3 observations, 3 650 candidats).

Chaque mesure avant/après a été prise dans un processus frais sur le même PC et le même DuckDB.
Le cache du système d'exploitation et la charge machine ne sont pas contrôlés ; ce ne sont pas
des garanties de latence inter-machines. Les rapports JSON locaux sont ignorés par Git.

| Mesure | Avant F3 | Après F3 |
| --- | ---: | ---: |
| Ouverture repository + intégrité, cas UI | 1,218 s | 1,212 s |
| Question après réponse, cas UI | 2,679 s | 2,642 s |
| Diagnostic après réponse, cas UI | **292,123 s** | **15,629 s** |
| `candidate_rows()` dans ce diagnostic | 288,160 s | 11,681 s |
| Conversion Pydantic en document JSON, cas UI | 2,085 s | 2,084 s |
| Encodage JSON du document, cas UI | 0,204 s | 0,205 s |
| Pic RSS, cas UI et document sérialisé | 3 344 Mo | 3 355 Mo |
| Diagnostic respiratoire, 696 candidats | 50,396 s | 4,009 s |

Le diagnostic le plus lent est **18,7 fois** plus rapide dans ce protocole. Le cas respiratoire
est **12,6 fois** plus rapide. L'empreinte SHA-256 du JSON complet du diagnostic et de la
question est identique avant/après pour les deux cas ; le nombre de candidats reste identique.
La comparaison des sept cas du test d'or v0.7 confirme **7/7 diagnostics et 7/7 questions**
identiques, incluant candidats, ordre, scores, provenance, mappings, abstentions et reçus.

## Cause et correction

Le calcul clinique n'était pas le goulet principal. Pour 26 000 assertions du cas respiratoire,
trois appels DuckDB recevaient chacun une liste Python d'environ 26 000 identifiants convertie en
paramètre `VARCHAR[]`. Chaque conversion prenait près de 16 secondes ; les jointures SQL elles-mêmes
prenaient entre 0,1 et 0,3 seconde. Avec 3 650 candidats, ces conversions dominaient les 288 s
de `candidate_rows()`.

Le repository construit maintenant trois ensembles temporaires de clés **dans DuckDB**, par
jointures sur le runtime existant : assertions canoniques sélectionnées, assertions sources et
records sources. Les requêtes de dérivation, provenance et locator s'y joignent sans réinjecter
de grandes listes Python. La connexion et les tables persistantes restent en lecture seule ; les
tables temporaires sont propres au processus. Aucun format, pipeline de build, profil ou calcul
`general_v1` n'a changé. Un test empêche la réintroduction d'une liste de source/assertion IDs
dans les paramètres de `candidate_rows()`.

Le test HTTP in-process sur la vraie base, avec sessions fictives isolées dans un répertoire
temporaire sous `data/staging/` et réseau externe bloqué, a confirmé `/`, `/expert`, la prochaine
question et la route d'analyse. Celle-ci a répondu `200` en **23,59 s** pour 3 650 candidats ;
les statuts `research_unreviewed: true` et `safety.status: not_evaluated` sont restés présents.

## Limite restante

Le résultat complet de ce cas fait **206 362 327 octets** avant transport et contient 3 650
candidats avec toute leur provenance. La matérialisation, la sauvegarde de session et la
sérialisation HTTP ajoutent encore plusieurs secondes au calcul de 15,6 s. Le parcours est très
loin des plus de 120 s initiaux, mais **pas encore de quelques secondes** pour ce grand cas.
Réduire davantage le temps perçu sans perdre les sorties exigerait une projection paginée/à la
demande des détails côté transport, ou un nouveau format runtime versionné ; cela doit être
étudié séparément avec des contrats et tests d'équivalence. Aucun candidat ni détail n'a été
supprimé dans F3 pour afficher artificiellement un meilleur chiffre.

## Reproduire

Après reconstruction locale du snapshot depuis les sources épinglées, sans réseau :

```text
uv run --offline --no-sync python scripts/profile_v07_f3.py --case examples/general/respiratory-common.json --output data/staging/f3-respiratory.json
uv run --offline --no-sync python scripts/compare_general_v1_runtime.py --output data/staging/f3-golden.json --expected tests/golden/v0.7-general-v1-sha256.json
uv run --offline --no-sync python scripts/smoke_v07_f3_http.py --case examples/general/respiratory-common.json
```

Le cas UI archivé de benchmark n'est pas commité. Il est facultatif et peut être remplacé par
une session **fictive** exportée localement. Aucun patient réel ne doit servir de benchmark.

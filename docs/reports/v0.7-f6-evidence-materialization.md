# `v0.7-F6` — matérialisation des assertions et de la provenance

Mesures Windows du 25 septembre 2026, sur le snapshot inchangé
`v0.7.0-general-dev-unreviewed` (hash de contenu
`bfda708aba44dcc5d12896ac7523d9d6bb577dea53bdc3810e499c15f64b1fb0`).
Les cas sont synthétiques ; ces mesures ne constituent ni validation clinique ni SLA.

## Baseline F5 avant modification

Le protocole `scripts/profile_v07_f5.py` crée une session locale éphémère, amorce la
question, puis chronomètre la route HTTP de diagnostic résumé dans un processus frais.
Le réseau non-loopback est bloqué. Les sorties chiffrées restent sous `data/staging/v0.7-f6/`
et ne sont pas versionnées. Le gros cas post-question provient d'une session fictive locale.

Sur le gros cas, F5 sélectionne 3 650 candidats et 152 168 assertions canoniques, ainsi que
152 280 assertions sources avec leurs dépendances et 152 104 locators. `candidate_rows()`
prend 5,10 s sur 12,54 s HTTP. La vérification d'intégrité et le démarrage sont réchauffés
par la question préalable ; leur coût n'est pas inclus dans ces durées. Le temps CPU est
voisin du temps mural, comme en F5. Le run de 206 Mo est complet avant la réponse ; son
écriture prend ~0,35 s et n'est pas le goulet.

## Trois stratégies mesurées avant le choix

`scripts/profile_v07_f6_strategies.py` sélectionne les mêmes candidats et compare des probes
en lecture seule. Les temps ci-dessous sont **des coûts de matérialisation isolés**, pas des
latences HTTP équivalentes. Le probe A projette 11 champs SQL, mais ne construit pas le run ;
le probe B utilise une table temporaire couvrant tout le snapshot et son coût à froid ne
comprend pas une éventuelle persistance/hash disque. Seule C a ensuite été intégrée et
comparée de bout en bout aux sorties F5.
La colonne F5 a été enregistrée avant la modification ; relancer le script sur F6 mesure
le repository F6, et non une nouvelle baseline F5. Pour la reproduire, exécuter ce script
avec le code du commit F5 `f1cc317`, en conservant les artefacts locaux du même snapshot.

| Stratégie, temps en secondes | Respiratoire, 26 006 assertions | Rare, 46 036 | Post-question, 152 168 |
| --- | ---: | ---: | ---: |
| F5 `candidate_rows()` complet | 1,67 | 2,14 | 4,80 |
| A — join SQL projeté, fetch seul | 0,89 | 0,99 | 1,73 |
| B — index dérivé, construction à froid + fetch | 3,05 | 3,08 | 3,20 |
| B — fetch chaud seul | 0,08 | 0,12 | 0,31 |
| C — validation Pydantic des assertions seules | 0,15 | 0,32 | 1,86 |
| C — extraction compacte des mêmes payloads | 0,03 | 0,05 | 0,17 |

Les probes A/B renvoient respectivement 26 021, 46 075 et 152 280 lignes à Python ; C
lit 26 006, 46 036 et 152 168 payloads canoniques. A intégré à `candidate_rows()`
pour essai complet a donné 12,78 s et **3 821 Mo** de pic RSS sur le gros cas, contre
12,54 s et 3 153 Mo pour F5. Le join du payload complet répète des données, augmente
la mémoire et annule son avantage isolé. Cette variante a été retirée avant livraison.

B exige une projection entière à chaque démarrage ou un nouvel artefact dérivé à gérer,
lier au hash du snapshot, invalider et reconstruire offline. Son gain chaud est réel, mais
la construction et le surcroît de mémoire ne justifient pas cette complexité pour cette
tranche. Aucun index persistant n'est livré et aucun snapshot n'est modifié.

## Solution retenue : assertion de scoring compacte

Le repository conserve les mêmes requêtes SQL F5 et la provenance détaillée. Il décode chaque
payload canonique vérifié en une structure interne immuable à cinq champs : ID, sujet,
relation, objet conceptuel éventuel et polarité. Les autres champs canoniques n'entrent pas
dans `general_v1` ; les objets non conceptuels restent ignorés comme avant. Ce type interne
ne change ni contrat public, ni mathématique, ni tables, ni manifeste. Toutes les contributions
et leur provenance sont toujours construites avant de finaliser le run.

La sécurité de cette projection repose sur le build canonique validé et sur l'intégrité forte
du snapshot vérifiée avant ouverture en lecture seule. Le test synthétique compare chaque
champ projeté au contrat canonique d'origine ; le test eager/lazy et les sorties d'or
comparatives restent en place.

| --- | ---: | ---: |
| Respiratoire HTTP total | 4,17 s | **3,89 s** |
| Respiratoire `candidate_rows()` | 1,59 s | 1,45 s |
| Respiratoire pic RSS | 2 088 Mo | **2 035 Mo** |
| Rare multisystème HTTP total | 5,25 s | **4,76 s** |
| Rare `candidate_rows()` | 2,01 s | 1,67 s |
| Rare pic RSS | 2 256 Mo | **2 160 Mo** |

| Gros cas pic RSS | 3 153 Mo | **2 856 Mo** |
| Gros cas run complet | 206 366 522 o | **206 366 522 o** |

Les variations de `model_dump`, du cache OS et de la GC montrent que ces mesures ponctuelles
ne sont pas un SLA. Le gain net du grand parcours est 3,04 s (24,2 %) dans ce protocole.
La réponse HTTP initiale et l'index local F4 restent inchangés. Les 7 diagnostics et
7 questions d'or du vrai snapshot gardent leurs empreintes JSON exactes. Une comparaison
supplémentaire du résultat complet du gros cas entre le commit F5 et F6 donne, des deux
côtés, 3 650 candidats, 206 362 327 octets sérialisés et SHA-256
`f7719b47361a705651cea1e3470432e52bc1f2c147bb3366eff3531042875e0d`.
Le run contient en plus son enveloppe de session ; ses 206 366 522 octets sont inchangés.

## Reproduction et limites

```text
python scripts/profile_v07_f6_strategies.py --case examples/general/respiratory-common.json --output data/staging/v0.7-f6/strategies-respiratory.json
python scripts/profile_v07_f6_strategies.py --case examples/general/rare-multisystem.json --output data/staging/v0.7-f6/strategies-rare.json
python scripts/profile_v07_f6_strategies.py --case data/staging/ui-smoke-sessions-20260925/session-9855a2f5-817c-4b17-8d78-e0de387e203b/session.json --output data/staging/v0.7-f6/strategies-big.json
python scripts/compare_general_v1_runtime.py --output data/staging/v0.7-f6/golden.json --expected tests/golden/v0.7-general-v1-sha256.json
python scripts/hash_v07_f6_case.py --root . --case data/staging/ui-smoke-sessions-20260925/session-9855a2f5-817c-4b17-8d78-e0de387e203b/session.json
```

Le dernier chemin est une **session synthétique locale ignorée par Git**, non une fixture
portable ; les deux premiers cas et les sept goldens sont portables si le snapshot local est
disponible. Les scripts ne téléchargent rien. Le probe A/B n'est pas une implémentation
clinique ; il ne produit donc pas de hash de run. La comparaison exacte des runs ne concerne
que les implémentations complètes F5 et F6. La limite principale demeure la construction
de 152 000 contributions/provenances et la sérialisation d'un résultat scientifique complet
de 206 Mo avant toute réponse. Un run partiel ou une provenance différée reste hors périmètre.

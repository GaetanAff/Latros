# `v0.7-F5` — profilage du run et latence résiduelle

Mesures d'ingénierie Windows du 25 septembre 2026, sur
`v0.7.0-general-dev-unreviewed` (hash de contenu
`bfda708aba44dcc5d12896ac7523d9d6bb577dea53bdc3810e499c15f64b1fb0`).
Aucune validation clinique ; aucun changement du score, du profil ou du snapshot.

## Baseline établie avant optimisation

`scripts/profile_v07_f5.py` exécute un cas **synthétique** par processus frais, bloque les
connexions non-loopback, utilise une session éphémère ignorée par Git, déclenche une question
pour réchauffer le repository, puis mesure la route `analyses?view=summary`. Les wrappers ne
changent pas les valeurs ; ils chronomètrent les phases. Les mesures sont des temps muraux sur
ce PC, sans contrôle des caches système, et ne constituent pas un SLA. La comparaison des trois
cas sert à distinguer coût fixe et coût lié au volume de candidats. Les mêmes cas et le même
script seront utilisés après optimisation.

| Mesure avant F5 | Respiratoire courant | Rare multisystème | Gros cas post-question |
| --- | ---: | ---: | ---: |
| Candidats | 696 | 799 | 3 650 |
| Route HTTP résumé | 5,653 s | 7,005 s | 19,064 s |
| CPU du processus pendant la route | 5,656 s | 6,969 s | 18,984 s |
| `_compute()` (inclut requêtes) | 3,799 s | 4,819 s | 15,673 s |
| `candidate_rows()` | 3,016 s | 3,613 s | 11,693 s |
| Conversion `DifferentialResultV2.model_dump` | 0,149 s | 0,394 s | 1,113 s |
| Écriture/index du run entier | 0,063 s | 0,108 s | 0,354 s |
| Taille du run complet | 35 008 688 o | 62 442 157 o | 206 366 522 o |
| Réponse HTTP initiale | 11 620 o | 12 589 o | 14 072 o |
| Pic RSS | 2 066 Mo | 2 219 Mo | 3 026 Mo |

Sur le gros cas, les trois renommages atomiques mesurent ensemble 0,002 s. Aucun `fsync`
explicite n'est appelé dans le chemin actuel : l'atomicité du remplacement est conservée, mais
on ne revendique pas une durabilité après coupure électrique. Le volume réellement écrit avant
réponse est le run complet (~206 Mo) plus l'index (~447 Ko) et le petit état de session.
La construction du résumé est inférieure au milliseconde dans la résolution du chronomètre.

### Décomposition du gros cas

`candidate_rows()` matérialise 152 168 assertions canoniques, 152 280 lignes sources,
152 104 locators et 4 818 désignations. Le profil SQL mesure notamment :

| Opération | Temps observé |
| --- | ---: |
| Sélection des payloads d'assertions canoniques | 2,398 s |
| Seconde sélection des mêmes IDs vers une table temporaire | 2,282 s |
| Sélection des libellés avec un paramètre `VARCHAR[]` de 3 650 IDs | 2,282 s |
| Source assertions, records et jointures de provenance | ~1,6 s |
| Validation Pydantic de 152 168 assertions | ~2 s avec `cProfile` (mesure instrumentée) |

`cProfile` ralentit ce même appel de 11,7 à 14,7 s. Ses 8,96 s dans le chargement de modules
pendant les appels DuckDB sont un effet potentiel du profiler/binding Python, non une durée
additionnelle à sommer aux chronomètres non profilés. Les valeurs du tableau principal sont
issues de passes **sans** `cProfile`.

La quasi-égalité CPU/temps mural et le fait que l'écriture ne représente qu'environ 2 % du
temps HTTP indiquent que le goulet est l'extraction/matérialisation des candidats et de leur
provenance, **pas** le disque ni le transport F4. `strategy._result_candidate` (3 650 appels)
prend 0,037 s ; l'essentiel des objets Pydantic sont les assertions construites dans
`candidate_rows()`. La sélection d'observations, la génération des IDs, le reçu et la réponse
HTTP sont mineurs en comparaison.

## Options à comparer avant décision

| Option | Borne du gain direct d'après la baseline | Coût/risque à mesurer |
| --- | ---: | --- |
| A — JSON monolithique optimisé | écriture 0,354 s ; conversion Pydantic 1,113 s | préserve naturellement le format, mais ne peut éliminer les ~15,7 s du calcul |
| B — run shardé | au mieux 0,354 s d'écriture gagnée | 3 650 fichiers/candidats, atomicité multi-fichiers et lecture expert plus complexes |
| C — DuckDB/Parquet/JSONL des runs | même borne de 0,354 s sur l'écriture seule | nouvelle migration et contrôle d'intégrité, sans effet sur `candidate_rows()` |
| D — différer des détails | gain potentiel plus grand | impossible sans protocole explicite garantissant run complet, immuable et auditable avant réponse |

La baseline seule ne justifie pas un changement de format. Le choix final et les mesures après
optimisation sont consignés ci-dessous.

Le troisième cas est une session fictive locale ignorée par Git ; elle peut être remplacée
par un autre cas synthétique. Les fichiers de mesure ne contiennent ni patient ni résultat
médical complet.

## Décision après mesure : conserver le run monolithique

La tranche garde l'option **A, format F4 inchangé**, et rejette B/C pour cette passe : même un
stockage à écriture instantanée n'enlèverait que 0,354 s sur le grand cas, alors que le coût
de migration, d'atomicité multi-fichiers et d'accès expert serait significatif. D n'est pas
retenue : différer la provenance ou les candidats rendrait le run incomplet à la réponse et
exigerait un nouveau protocole de finalisation/immutabilité. Une variante A qui supprime
seulement `model_dump` pourrait gagner au plus ~1,1 s, avec une réécriture plus risquée de la
sérialisation d'un résultat Pydantic complet. Le profil montre un levier plus grand dans le
repository DuckDB existant ; il a donc été traité en priorité. Aucun nouvel ADR de format de
run n'est nécessaire.

`candidate_rows()` sélectionnait deux fois les mêmes assertions canoniques et liait ensuite
3 650 IDs Python dans un paramètre `VARCHAR[]` pour les libellés. La sélection crée maintenant
une seule table temporaire contenant IDs et payloads ; les dérivations et libellés s'y joignent
sans seconde liaison de grande liste. La requête de correspondance garde aussi ses IDs dans une
table temporaire, et `candidate_rows()` refuse explicitement de la réutiliser si la liste
Python n'est pas exactement la même. Ces tables sont propres à la connexion DuckDB **ouverte en
lecture seule** ; aucune table persistante ni aucun artefact du snapshot n'est changé.

## Avant / après, même protocole

| Mesure | Respiratoire avant → après | Rare avant → après | Post-question avant → après |
| --- | ---: | ---: | ---: |
| Route HTTP résumé | 5,653 → **4,300 s** | 7,005 → **5,487 s** | 19,064 → **12,703 s** |
| `_compute()` | 3,799 → 2,454 s | 4,819 → 3,301 s | 15,673 → 9,317 s |
| `candidate_rows()` | 3,016 → 1,652 s | 3,613 → 2,111 s | 11,693 → 5,346 s |
| Pydantic `model_dump` du résultat | 0,149 → 0,143 s | 0,394 → 0,386 s | 1,113 → 1,111 s |
| Écriture/index du run | 0,063 → 0,064 s | 0,108 → 0,109 s | 0,354 → 0,357 s |
| Run complet | 35 008 688 → 35 008 688 o | 62 442 157 → 62 442 157 o | 206 366 522 → 206 366 522 o |
| Pic RSS | 2 066 → 2 088 Mo | 2 219 → 2 255 Mo | 3 026 → 3 147 Mo |

Le grand cas gagne **6,361 s (33,4 %)** dans ce protocole, au prix d'environ **121 Mo** de pic
RSS supplémentaire pour garder les payloads sélectionnés dans la table temporaire. Les cas
courant/rare gagnent respectivement 1,353 et 1,518 s. La réponse initiale reste 14 072 octets
sur le grand cas ; le run complet et l'index conservent leurs tailles. Les 7 diagnostics et
7 questions d'or du vrai snapshot ont la même empreinte JSON complète avant/après. Les tests
de sessions vérifient la reprise, le résumé, le détail et le run expert complet ; le test
spécifique compare le chemin de table temporaire à la sélection directe sur une fixture
inventée. Aucun score, rang, mapping, reçu ou statut n'est recalculé autrement.

Le temps historique F4 de 18,538 s et la baseline F5 de 19,064 s ont été pris à des moments
différents ; le gain attribuable à F5 est calculé **uniquement** sur les deux mesures du même
script F5. La mémoire et le CPU sont propres à ce PC. Le grand cas reste au-dessus de 10 s :
`candidate_rows()` prend encore 5,3 s pour ~152 000 assertions et locators, et le reste de
`_compute()` ~4 s pour matérialiser toutes les contributions/provenances que le run complet
doit conserver. Le compromis format/latence pourra être réévalué seulement si un profil futur
montre un changement du goulet.
